## 0. 何のために

謎解き（公演型・周遊・LINE 謎・Web 謎・持ち帰り謎）の**作品マスタを複数ユーザーで共有**し、
各ユーザーは**自分の参加記録（「買った」を含む）と得意傾向の統計**をそこに紐付けて残し、承認したフレンドにはステータスだけ見せる。
マスタの追加・修正はユーザーの「リクエスト」としてキューに溜め、**オーナーの指示で
このサーバーの Claude が調べて提案し、オーナーが承認して反映**する。

やらないこと:
- escape.id `/me/`（マイページ）・ブックマークへのアクセス。参加の有無・結果は常に手入力
- ログインが要るサイト・スクレイピング禁止サイト（X 含む）からの自動取得
- 定期バッチでの自動取得（実行は常にオーナー指示）
- trailcast への書き戻し（読むだけ）
- **フレンド以外への記録の表示**。マスタに出す他人由来の数字は「プレイ済み人数」「マイリスト登録者数」の 2 つだけ（§6.5）。成功率・評価平均は出さない
- **オーナーが他人の記録を分析する機能**（横断集計ビューも作らない）。分析は本人向けのみ
- ESCAPE.ID Hub への相談・申請（公開情報の読み取りに留める）
- 公式サイト・escape.id からの**画像取得**（Claude の補完処理を含む）。escape.id の `imageUrl` は保存も表示もしない。画像は全てユーザーが撮った写真（§3.4）

- 置き場所は **Cloudflare Workers + D1 で確定**。このサーバーは Claude の実行場所。

## 3. データモデル（要点）

詳細は [data-model.md](./data-model.md)。

- **作品 (work)** と **回 (run)** を分ける。escape.id URL は公演ごと（例 `e-usonohonya2026`）なので **run に付く**。再演・別会場・別名義は run を増やす。
- **団体 (organization)** は別名テーブルで改名・表記ゆれを吸収。run に当時の名義 `billed_as` を保存。
- **販売先 (shop)**、**出店 (market → market_edition → booth)** を持つ。持ち帰り謎の販路は複数あり得る前提で、販売サイトごとの run（`channel = sale`）＋出店の booth_item で追跡（data-model.md の `v_work_channels`）。
- **記録 (attempt)** はユーザーごと・作品ごとの「挑戦」。`status` = 買った / 進行中 / クリア / 失敗 / 断念。軽い記録は attempt 1 行だけ。詳しい記録は **進行ログ (session)** を複数ぶら下げる（日付・所要時間・同行者・メモ・場所）。
- 記録の評価項目: **難易度 (1-5)・物量 (1-5)・ジャンル（固定 8 種から複数選択）・通常メモ・ネタバレメモ（別列、本人のみ）**。本人向け統計で難易度別成功率・ジャンル別成功率などの「得意傾向」を出す（§3.2、data-model.md §6）。
- **フレンド**（招待リンク → 申請 → 承認の相互）には **v1 ではステータス（作品・status・日付）だけ**を見せる。細かい公開範囲設定は P11（§6.3、決定）。フレンド以外には一切見せない。
- **画像**は全てユーザーが撮った写真（会場のキービジュアルパネル / クリアパネル / その他）。記録に属し R2 に置く。v1 では本人のみ表示（フレンドへの写真表示は公開範囲設定と同時に）。ネタバレ印付きの写真は常に本人のみ（§3.4）。マスタ側に画像は持たない。
- **購入**は attempt の `status = purchased`（買った）で表す。購入専用テーブルは持たず、買った場所・価格も記録しない。
- **マイリスト (wishlist)**: 「これから遊びたい作品」を attempt とは別に登録。中身は本人のみ。外すのは手動のみで、プレイ済みの作品には印が付く（§3.5）。
- **匿名の人数**: 作品一覧・作品ページに「プレイ済み n 人」「マイリスト n 人」を全ユーザーに表示。誰が、は出さない。少人数はぼかす（§6.5）。
- **マスタは全ユーザー共有。記録・統計は本人のみ（フレンドにはステータスだけ、全員には匿名人数だけ）。一般公開機能は作らない**（決定）。
- 提案 (proposal) は**フィールド単位の差分**。各フィールドに出典 (source) と取得日時。却下はフィンガープリントで記憶。

### 3.1 ステータスと統計（要点）

| status | 意味 | 成功率の分母 |
|---|---|---|
| `purchased` 買った | 持ち帰り謎など、買ったが未プレイ | 含めない |
| `in_progress` 進行中 | 周遊・持ち帰り・Web 謎を途中まで | 含めない |
| `cleared` クリア | 成功 | 含める（分子） |
| `failed` 失敗 | 公演で時間切れ等 | 含める |
| `dropped` 断念 | 途中でやめた | **既定は含めない**、トグルで「失敗扱い」に切替 |

成功率 = cleared / (cleared + failed) を既定。再挑戦は attempt が複数行になるので「挑戦ベース」と
「作品ベース（最新 attempt のみ）」の 2 表示。本人向け統計の一覧は data-model.md §6。

### 3.2 評価項目（難易度・物量・ジャンル・ネタバレメモ）

| 項目 | 推薦 | 代替 |
|---|---|---|
| 難易度（自分にとって） | 1-5 の 5 段階、NULL 可（決定） | 3 段階 → 集計の粒度が粗い |
| 物量 | 1-5、NULL 可（決定） | 所要時間で代替 → 公演は制限時間で頭打ちになり測れない |
| ジャンル | **固定リストから複数選択**。初期 8 種 = ひらめき / 論理 / 物量 / ストーリー / 探索 / 大謎一発 / 協力 / 体験・演出（決定）。オーナーがリストを管理、追加はリクエスト | 自由タグは表記ゆれで集計できないので v1 は持たない |
| ネタバレメモ | `spoiler_memo` を通常 `memo` と別列。表示は既定で畳み、タップで展開。**本人のみ。認可層で常に返さない。設定項目なし（決定）** | — |

本人向け統計は trailcast の記録項目（種類・成否・団体/場所）と「ふりかえり」構想（件数・合計/平均/最大最小。UI は未実装）を参考にし、難易度別・ジャンル別・形式別の成功率などの「得意傾向」を出す（data-model.md §6）。

### 3.3 ルーム型・常設の扱い

- `work.kind = room`。常設は `run(channel=performance, venue_id=店舗, start_on NULL 可, end_on NULL, is_permanent=1)` の 1 行。終了したら `end_on` を入れる。
- 一覧は **都道府県 → 店舗 (venue) → 遊べる作品** で並べる（`v_room_by_venue`: `end_on IS NULL OR end_on >= today`）。作品の再演（同じ部屋の復活）は run を増やす。
- 取得元: escape.id に載っていればユーザー指定 URL で取れる（ラベル「ルーム型」、終了日なし）。**横断一覧サイトは無く、SCRAP 等の店舗一覧は JS 描画で取れない**。→ ルーム型は「店舗ごとに公式サイト URL をユーザー/オーナーが渡し、Claude が WebFetch で読む」か手入力。詳細は sources.md §2。
- escape.id は形式を区別していない前提。`work.kind`（room / hall / stroll 等）は Claude が説明文・公式サイトから推定して提案し、**オーナーが承認時に確定**する。`run.escape_type_raw` は生値を参考として残すだけ。常設かどうか（`is_permanent`）も同様に推定→承認。

### 3.4 画像

画像は **ユーザーが自分で撮った写真だけ**。マスタ側に画像は持たず、システム（Claude 含む）が公式サイト・escape.id から画像を取りに行くことはしない。escape.id の `imageUrl` は保存しない。

| 項目 | 内容 |
|---|---|
| 種類 `kind` | `key_visual`（会場に掲示されたキービジュアルパネル）/ `clear_panel`（クリア・成功パネル）/ `other`（記念写真など） |
| 所属 | 記録 (attempt) に属する。本人のもの。v1 ではフレンドに表示しない（公開範囲設定を入れる Phase で、メモ相当の範囲として扱う） |
| ネタバレ | `spoiler` フラグ。本人表示は既定で畳む。**ネタバレ印付きの写真は常に本人のみ。認可層で固定、設定なし（決定）** |
| 置き場 | R2 **非公開バケット**。公開 URL は作らず、Worker が認可してから返す |
| 縮小・EXIF | クライアント（Canvas）で最大 1600px + 320px サムネを生成して PUT。再エンコードで EXIF（位置情報含む）が落ちる。Worker でも EXIF 残存・MIME・サイズを検査し、不合格は拒否 |
| 上限 | 1 記録 4 枚、1 枚 2MB（縮小後）、1 ユーザー 300MB（R2 無料枠 10GB ÷ 30 人程度）（決定） |
| 通報・削除 | フレンドが通報 → オーナーが非表示（`removed_at`）→ 7 日後に R2 から削除。通報者・理由は `image_report`。本人削除は即時 |

リサイズの比較: (I-1) クライアント Canvas ← **推薦**（無料、EXIF 除去を兼ねる、Worker CPU を使わない）。(I-2) Images Transformations（`/cdn-cgi/image/`）: 公開 URL 前提で非公開画像に使えない。(I-3) Images Storage: $5/10 万枚、過剰。

注意点（アプリ内に明記）:
- 撮影の可否は会場のルールに従う。撮影禁止のパネル・室内は上げない。
- 写真は本人（将来は許可したフレンド）にしか見えない。全体公開の機能は無く、作らない。
- パネルには主催の著作物が写る。私的・限られた範囲での共有に留め、SNS 等への転載は各自の判断と責任（アプリは転載機能を持たない）。

### 3.5 マイリスト（これから遊びたい）

- `wishlist(user_id, work_id, created_at, memo)` PK(user_id, work_id)。記録 (attempt) とは独立。中身（どの作品か）は**本人のみ**。フレンドにも見せない（v1）。
- **外すのは手動のみ（決定）。** 遊び始めても、買っても、クリアしても自動では外れない。一覧では本人の attempt を結合して「買った / 進行中 / クリア済み / 失敗 / 断念」の印を付け、「未プレイだけ表示」のフィルタで次に遊ぶものを選べるようにする。印は本人の最新の記録（`attempt_no` DESC）のステータス。
- **「未プレイ」= その作品の記録 (attempt) が 1 件も無いこと（P3 で決定）。** 買った・進行中・断念の記録があれば未プレイには含めない。
- `memo` は列だけ残し、P3 では画面を作らない（入力も表示もしない）。
- **escape MCP の watchlist とは別物。** あちらは MCP サーバー自身の DB に入る「日程監視用の気になるリスト」で、nazo-tracker からは読み書きしないし同期もしない。
- 本人向け統計に「マイリスト件数」「うちプレイ済みの割合」を足す。

### 3.6 trailcast の扱い（比較）

| 案 | 内容 | メリット | デメリット | 実装 | 運用 |
|---|---|---|---|---|---|
| T-1 一方向インポート（推薦） | PDS を `listRecords` で読み、1 post = 1 attempt（+session）の**提案**を作る。`source_ref` に at-uri。冪等 | 構造化して集計できる。trailcast 無改変 | 以後は nazo-tracker を正にする運用が要る | 小 | 無 |
| T-2 参照リンクのみ | 閲覧時に PDS を読む | 二重化しない | 集計に使えない。マルチユーザーと噛み合わない | 小 | 無 |
| T-3 PDS を正にする | 記録を独自 Lexicon で PDS に書き、D1 は索引 | AT Proto らしい | Bluesky 以外のユーザーが使えない。工数大 | 大 | 中 |

**推薦 T-1。** 76 件は Claude がタグ・本文から作品候補を当てて提案、オーナーが一括承認。

## 5. 「Claude が補完する」実行形態（要点）

詳細は [agent-pipeline.md](./agent-pipeline.md)。

| 案 | 内容 | メリット | デメリット | 実装 | 運用 |
|---|---|---|---|---|---|
| E-1 Claude Code セッションで `/process-queue`（推薦） | SSH → `c nazo-tracker` → 「キュー処理して」。CLI でキュー取得、MCP/WebFetch で調査、提案 POST | 今の運用そのまま。MCP・サブスク認証を流用。失敗時に対話で直せる | tmux を開く必要 | 小 | 無 |
| E-2 Web の「処理開始」→ systemd timer が旗を見て `claude -p` | tmux 不要 | 実質バッチ。`claude -p` の MCP/権限/ログ/通知の整備。暴走時に止めにくい | 中 | 小〜中 |
| E-3 Worker にリモート MCP を生やす | ツール型で型安全 | E-1 の CLI と重複。認証実装が増える | 中 | 小 |

**推薦 E-1（+ CLI）。** E-2 は同じ CLI を `claude -p` から呼ぶだけで後付け可。

### 承認段階（比較）

| 案 | 流れ | 向く場面 |
|---|---|---|
| A-1 事前選別 | オーナーがリクエストを `triaged` / `rejected` に振ってから Claude へ | スパム除去。全件は見ない |
| A-2 事後承認 | Claude の結果は全て `proposal.pending`。差分を見て承認 | 既定。マスタ変更・マージ・インポート |
| A-3 条件付き自動反映 | **サーバー側ルール**で「出典 = escape.id（MCP）」「重複候補なし」「信頼度 ≥ 0.9」なら即反映、7 日間取り消し可 | 新規公演の登録 |

## 6. プライバシー・フレンド・認可

### 6.1 原則
- 記録・統計は **本人のみ**。承認済みフレンドには **ステータスだけ**（v1）。フレンド以外・未ログイン・検索エンジンには一切出さない。一般公開の共有リンクは作らない（決定）。
- **マスタに出す他人由来の数字は 2 つだけ**: 作品ごとの「プレイ済み人数」と「マイリスト登録者数」。全ユーザー（未ログイン含む）に人数だけ出し、誰が、は出さない。少人数はぼかす。成功率・評価の平均・難易度の平均は出さない（§6.5、決定）。ログイン中でフレンドがいれば「フレンド n 人がプレイ済み」も自分視点で出す。
- **ネタバレメモとネタバレ印付きの写真は本人のみ。** 認可層で固定し、設定項目は作らない（決定）。
  - ネタバレ本文は初期 HTML に含めず、表示操作時に本人認可済みの断片 URL から取得する（`Cache-Control: no-store, private`・`X-Robots-Tag: noindex`）。断片 URL の認可は P3 で owner-only を必須とする。
- **オーナーが他人の記録を見る・分析する機能は作らない**（決定）。分析機能は各ユーザーが自分の記録を見る本人向け機能。

### 6.2 フレンド
- 申請 → 承認で相互フレンド。片方向フォローは無い。拒否・解除・ブロックができ、ブロック中は申請も表示も不可（相手には「見つからない」と同じ応答）。
- 探し方: **招待リンク `/f/<friend_code>` のみ**（コードは再発行可、NULL で招待停止）（決定）。表示名検索は作らない。Bluesky のフォロー関係から候補を出すのは後の Phase。

### 6.3 フレンドに見せる範囲

**v1 の挙動（決定）**: フレンド全員に対し、作品ごとの `status`（買った / 進行中 / クリア / 失敗 / 断念）と日付（`finished_on` / `started_on`）だけを固定で見せる。評価・メモ・同行者・写真・進行ログは見せない。記録ごとの非表示設定も v1 には無い。作品ページの「フレンド n 人がプレイ済み」はこの固定範囲で成り立つ。

後の Phase（P11）で入れる候補: ユーザー既定の share level（`none` / `status` / `rating` / `memo`）+ 記録ごとの `hidden` 上書き。フレンドごとの個別設定・グループは更に後。

データモデルの扱い（決定: **列は v1 から持つ**）: `user.default_share_level`（既定 `status`、v1 は UI 無しで固定値）と `attempt.share_override`（v1 は常に NULL）を最初から定義し、`asFriendOf` の射影も level 別の型で作っておく。v1 では status 以外の分岐を UI から到達不能にする。

### 6.4 認可の実装
- 記録系ルートは HTML の `/records/*`（本人）、`/api/me/*`（本人、JSON を出す段階で足す）と `/api/friends/:userId/*`（フレンド閲覧）のみ。後者は **friendship(accepted) かつ block 無し** を必ず確認し、満たさなければ 404。v1 は `status` 射影のみ返す。
- リポジトリ層: `scopedTo(viewerId)` が返すハンドルに `own()` と `asFriendOf(targetUserId)` の 2 口。`asFriendOf` は friendship を検証し、level 別の列セットしか返せない型にする。**`spoiler_memo` と `spoiler=1` の画像は `own()` の型にしか存在しない**。ネタバレの応答（`spoilerResponse`）は `own()` だけが返す brand 付きの `OwnAttempt` しか受けない（auth.md §6）。これ以外に attempt / session / image を読む経路を作らない。
- **オーナー**: 承認 UI・マスタ編集（`/admin/*`）・リクエスト一覧・通報対応・genre 管理。他人の記録を見る画面・API・集計ビューは作らない。フレンドとしてのオーナーは一般ユーザーと同じ扱い。
- **agent トークン**: マスタ読、リクエスト読、提案・出典書き。記録系・フレンド系・画像は 403。
- **D1 管理者権限について**: オーナーは Cloudflare 管理者として技術的に全行を読める。アプリ内「データの扱い」ページに「障害対応・復旧以外で生データを開かない。分析機能は本人向けのみ」と明記する。`wrangler d1 export` は障害時のバックアップ用途に限り、取得物は `~/.local/share/nazo-tracker/`（0700）に置いて 30 日で消す。運用監視用の総数（ユーザー数・記録総数・画像数・R2 使用量）はオーナー画面に出す（決定）。総数のみで、ユーザー別の内訳は持たない（`v_ops_totals`）。
- **削除**: 退会で消す範囲と手順は auth.md §6（退会）を参照。

### 6.5 匿名の人数（プレイ済み・マイリスト）

| 論点 | 決定 | 捨てた案 |
|---|---|---|
| 「プレイ済み」の定義 | `status ∈ {cleared, failed}` の attempt を持つ **ユーザー数（DISTINCT user_id）**。`dropped` / `purchased` / `in_progress` は含めない | dropped を含める → ユーザー判断で除外 |
| マイリスト人数 | `wishlist` の DISTINCT user_id（手動で外すまで数える） | — |
| ぼかし | **5 人未満は「少数」**、5 人以上は実数。0 人は作品一覧では出さず、作品ページでは「まだ記録はありません」 | 閾値 3 → ユーザー判断で 5 に |
| オプトアウト | **ユーザー単位** `user.exclude_from_counts`（既定 OFF = 含める）。ON なら両方の人数から外れる。P11 の記録ごと `hidden` も人数から外す | オプトアウト無し / 記録ごとのみ |
| 集計方法 | **その都度 COUNT**（`GROUP BY work_id`、INDEX(work_id, status, user_id) と wishlist(work_id)）。一覧 50 件で 2 クエリ。数万行までは D1 無料枠で問題なし。超えたら Cache API で 5 分キャッシュ | カウンタ列 → DISTINCT・オプトアウト・hidden との整合がずれる |
| フレンド n 人との関係 | 作品ページは「プレイ済み 12 人 · マイリスト 5 人」+（ログイン・フレンドありなら）「うちフレンド 2 人」。フレンド数は share で見えている分を数えるので、オプトアウトした友人がいると「少数」なのに「フレンド 5 人」になり得る。許容し、UI では別行に出す。フレンド n 人の「プレイ済み」も cleared + failed で揃える | フレンド数も opt-out に従わせる |

**人数以外の匿名集計（成功率・平均難易度・平均評価など）は v1 では出さない。将来は出したい（決定）。** 出すときの前提:
- 同じぼかし閾値（分母 5 人未満は出さない）と、同じオプトアウト・hidden の尊重。
- 平均・成功率は分母 5 人以上でも、1 人の記録追加で値が動くため「直前との差」から個人の評価が推測できる。対策候補: 値を丸める（成功率 10% 刻み、平均 0.5 刻み）、分母が閾値を超えた直後は表示しない（例: 8 人以上から）、更新を日次にまとめる。実装時に 1 つ選ぶ。
- 評価のばらつき（最小・最大・分布）は出さない。出すのは中央値か丸めた平均だけ。
- フレンド n 人との組み合わせで差分を取られないよう、フレンド側には集計値を出さない（人数のみ）。

差分からの特定について: 閾値未満を「少数」にしても、(1) 自分が記録した直後に表示なし（作品ページは「まだ記録はありません」）→「少数」に変わる、(2) フレンド表示で知っている人数を引く、(3) 特定の日に誰かが遊んだと外部で知っていて数字の増加を見る、で「他に 1 人いる」程度は推測できる。得られるのは人数の増減だけで、誰かは分からない。本アプリはフレンド以外に status を出さないので、名前と結び付くのは「外部で既に知っている」場合だけ。この残余リスクはオプトアウトで本人が回避できる、と「データの扱い」ページに書く。

残余リスク（未対策）: 本人がオプトアウトや記録の足し引きをすると、5 人の境界（「少数」⇔「5 人」）で他の人数が分かる。複数アカウントを用意すれば、同じやり方で「少数」の内訳も読める。いずれも分かるのは人数だけで、誰かまでは特定できない。対策（閾値の引き上げ・日次更新）は未導入。

## 10. 決定事項 / 未決事項

### 決定（ユーザー回答・本書で固定）

**基盤**
- 置き場所: Cloudflare Workers + D1 + R2。ドメイン `nazo.shino3.net`。このサーバーは Claude 実行場所。
- スタック: Hono + Hono JSX (SSR) + Drizzle。

**認証**
- Google と Discord から開始、Bluesky（AT Proto OAuth）は P6、X は見送り。
- 個人情報（メール等）は保持しない。provider + subject のみ。
- 復旧: 2 プロバイダ紐付けの推奨 + 復旧コード + オーナーの手動付け替え。

**補完パイプライン**
- 実行はオーナー指示（E-1: Claude Code セッションで `/process-queue` + `nazo-admin` CLI）。定期バッチにしない。
- Claude の権限は「提案を書く」まで（W-1: REST API + agent トークン）。自動反映の判定はサーバー側。
- escape.id 由来の新規 work / run は自動反映、7 日間取り消し可。update / merge / link / インポートは常に pending。
- `work.kind` と `is_permanent` は Claude が推定して提案し、オーナーが承認時に確定。ラベル→kind の自動変換表は持たない。

**データモデル**
- work と run を分け、escape.id URL は run に付く。団体は alias で改名を吸収。
- ステータスは purchased / in_progress / cleared / failed / dropped。予約済みは持たない。購入専用テーブルは持たず、買った場所・価格も持たない。
- 成功率既定 = cleared / (cleared + failed)。dropped は除外（トグルで含められる）。再挑戦は別 attempt 行。
- 持ち帰り謎の販路は run(channel=sale) + booth_item、作品ページは `v_work_channels`。
- ルーム型は work.kind=room + 常設 run（end_on NULL, is_permanent）。一覧は都道府県→店舗→作品。初期データは店舗公式 URL（ユーザー/オーナーが渡す）+ escape.id 掲載分。
- 記録に難易度・物量（各 1-5）・ジャンル（固定 8 種: ひらめき / 論理 / 物量 / ストーリー / 探索 / 大謎一発 / 協力 / 体験・演出、複数選択）・ネタバレメモ（別列）を持つ。同行者は自由テキスト。
- trailcast は一方向インポート（T-1）、P5 で実施。統計は trailcast の記録項目・「ふりかえり」構想を参考にする。

**プライバシー・フレンド・画像**
- マスタ共有。記録・統計は本人のみ。一般公開機能は作らない。
- マスタに出す他人由来の数字は「プレイ済み人数」「マイリスト登録者数」の 2 つ（全ユーザーに人数のみ）。**5 人未満は「少数」、0 人は「—」**。「プレイ済み」= cleared + failed（dropped / purchased / in_progress は含めない）。その都度 COUNT、生の数値は API で返さない。
- 人数へのオプトアウトはユーザー単位（既定: 含める）。P11 の記録ごと hidden も人数から除外。
- 人数以外の匿名集計（成功率・平均難易度・平均評価）は **v1 では出さない。将来検討**（§6.5 の前提に従う）。
- マイリスト（これから遊びたい）を attempt と別に持つ。中身は本人のみ。**外すのは手動のみ**（遊んでも買っても自動では外れない。プレイ済みの印を付ける）。escape MCP の watchlist とは無関係。
- フレンド表示は v1 では status（作品・status・日付）に固定。公開範囲設定は P11。`default_share_level` / `share_override` の列は v1 から持つ。
- 運用監視用の総数（ユーザー数・記録総数・画像数・R2 使用量）をオーナー画面に出す。総数のみ、ユーザー別内訳なし。
- オーナーが他人の記録を分析する機能・横断集計ビューは作らない。分析は本人向け（得意傾向）のみ。
- フレンドは招待リンクのみで申請→承認の相互。作品ページに「フレンド n 人がプレイ済み」を出す。
- **ネタバレメモとネタバレ印付きの写真は本人のみ。** 認可層で固定、設定項目なし。
- 画像は全てユーザーが撮った写真（key_visual / clear_panel / other の 3 種）で記録に属する。公式サイト・escape.id から画像を取らない（`imageUrl` は保存しない）。R2 非公開バケット、クライアント縮小で EXIF 除去、Worker 経由で認可配信。上限 1 記録 4 枚・1 枚 2MB・1 ユーザー 300MB。
